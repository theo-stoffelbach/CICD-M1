Pourquoi workflow_run et pas push ?

Un déclencheur push: [main] lance CI et CD en parallèle : la CD peut builder et pusher une image d'un commit dont les tests n'ont pas encore tourné. workflow_run garantit l'ordre et la condition de succès.

Double tag :latest + :sha

Watchtower suit :latest pour l'auto-update. Le tag SHA permet de tracer exactement quel commit est en production et de rollback en pointerant sur un SHA précédent si besoin.

Critère barème — choix DevOps justifiés

Justification des choix techniques

Outil choisi Alternatives Pourquoi ce choix
GitHub Actions Jenkins · GitLab CI · CircleCI Intégré nativement à GitHub, GITHUB_TOKEN fourni automatiquement pour GHCR, marketplace riche, zéro infrastructure CI à gérer
GHCR Docker Hub · Harbor · ECR Même écosystème que GitHub Actions, auth via GITHUB_TOKEN sans secret supplémentaire, packages liés au repo, gratuit pour dépôts publics
Watchtower Flux (GitOps) · ArgoCD · deploy SSH manuel Solution légère adaptée à un NAS Ugreen (pas de Kubernetes), déploiement zero-config via label container, polling GHCR natif
FastAPI + Python 3.14 Django · Flask · Node/Express Réutilise le code du module Tests précédent, async natif, OpenAPI auto-généré, type hints pour la robustesse
React 19 + Vite Next.js · Vue · Vanilla JS SPA légère servie par nginx, Vite build ultra-rapide, migration naturelle depuis le HTML/JS vanilla du module précédent
PostgreSQL 16 MySQL · SQLite · MongoDB ACID, robuste en production, postgres:16-alpine image légère, support natif SQLAlchemy, adapté au modèle relationnel (utilisateurs, parties)
NPM (Nginx Proxy Manager) Traefik · Caddy · HAProxy Déjà déployé sur le NAS, UI web pour Let's Encrypt, configuration via interface sans recharger l'infra
